# Prompt for ChatGPT 5.6 Pro

Ты — независимый principal product engineer, ML lead и App Store release owner. Перед тобой фактический handoff iOS-приложения Shafin Multitool / SET OS. Изучи ВСЕ приложенные файлы и изображения до ответа. Не соглашайся с документацией автоматически: отличай source-backed поведение, тестовый контракт, fixture/mock, исторический claim и реальное release evidence.

## Главная задача

Дай Codex конечное направление, которое превратит текущий большой, но незавершённый checkout в работающий, измеримо полезный, отполированный App Store 1.0. Пользователь устал от циклов moodboard/редизайна. Не предлагай новый moodboard, новую параллельную дизайн-систему или очередной концептуальный этап. Визуальный authority уже существует: SET OS v2.6.

Ключевая ценность 1.0: Camera Coach должен по реальному кадру корректно определить практическую композиционную проблему либо сохранить хороший кадр, дать короткое действие вроде «смести объект левее» или «подойди ближе», затем проверить результат после движения. Scene/Generator/AR/Storyboard — вторичный flow, который нужно либо довести до честного ship-quality, либо обоснованно сократить для 1.0.

## Непереговорные факты и ограничения

- Текущий checkout грязный и не является воспроизводимым release candidate.
- Более широкий ML eval на 207 случаях имеет pass rate 0.671498, expected-action hit 0.748792, forbidden-action violation 0.188406 и good-frame preservation 0.875. Это недостаточно. Более ранний perfect 107-case run потенциально узок, переобучен или contaminated.
- DETR/NIMA присутствуют, но их provenance не закрыт. Ожидаемая `compact_neural_evidence_net` отсутствует. Большой GGUF исключён из Release. Remote VLM — незавершённый environment-selected transport, не production backend.
- Пять provenance/legal проверок намеренно блокируют текущий release gate.
- Нет signed archive/Apple validation, текущего green full suite и обязательной physical-device матрицы.
- Симулятор не доказывает ARKit, camera/mic, Photos, REC/playback, A/V sync, thermal и hardware timing.
- Никогда не требуй iPhone 17 Pro; он запрещён владельцем для этого проекта.
- Не предлагай редактировать thesis/litreview, выполнять destructive Git operations или менять CommercialShell routes/async teardown/accessibility IDs без явной миграционной необходимости.
- Не утверждай, что сам запускал код, тесты или видел какие-либо локальные пути помимо содержимого реально приложенных файлов.

## Что нужно решить, а не перечислить

1. Сформулируй один рекомендуемый App Store 1.0 cut и явно убери всё, что отвлекает от ship.
2. Выбери целевую ML architecture. Сравни минимум:
   - текущий deterministic + DETR/NIMA стек;
   - Apple Vision + deterministic geometry;
   - обучаемую compact Core ML модель;
   - opt-in remote VLM только для Deep Review.
   Назови победивший вариант, переходный путь, удаляемые/заменяемые зависимости и причины.
3. Дай конкретный dataset/training/eval protocol:
   - operational label taxonomy, пригодную для UI actions;
   - семь классов матрицы: single person, two people, object/food, interior, street/landscape, difficult light, already-good frame;
   - split по source shoot/scene, leakage guard, deduplication, annotation QA, hard negatives;
   - calibration/abstention, before→after verification;
   - baseline/candidate comparison и человеческую слепую оценку;
   - точные release thresholds, при которых feature разрешено включить.
4. Прими backend decision: backend не нужен для 1.0 либо нужен минимальный opt-in Deep Review. Если нужен — укажи provider-neutral API schema, auth, quotas, consent, redaction, encryption, region, retention/deletion, cost ceiling, timeout/fallback и observability. Live advice не должен зависеть от сети.
5. Реши iPhone-only против iPhone+iPad для 1.0.
6. Закрой release path: provenance/notices, privacy/App Privacy, signed archive, Apple/ASC validation, TestFlight, crash/perf/quality gates и physical-device matrix.
7. Укажи, какие текущие UX дефекты являются blockers, а какие можно не трогать до 1.1.

## Обязательный формат ответа

Ответ — один самодостаточный Markdown-документ со следующими разделами:

### 1. Brutal executive verdict

- Готовность по шкале 0–100 с объяснением.
- Три главные причины, почему продукт ещё не ship.
- `DO NOT BUILD`: что прекратить делать сейчас.
- Точный рекомендуемый 1.0 cut.

### 2. Verified system map

Таблица: subsystem → implemented/source-backed → test-backed → fixture/doc-only → missing → release impact. Не выдавай количество тестов за их прохождение.

### 3. Blocker register

P0/P1/P2 с ID, evidence из приложений, root cause, пользовательским риском и критерием закрытия. Отдельно пометь противоречивые или устаревшие документы.

### 4. Recommended 1.0 architecture

Одна целевая схема приложения и границы ownership: capture, feature extraction, composition inference, advice planner, verification loop, persistence, Scene Mode, optional backend. Покажи data flow и failure/abstention behavior.

### 5. ML/model delivery plan

Укажи точные:

- labels и запрещённые советы;
- dataset artifacts и versioning;
- train/validation/test split rules;
- baselines и ablations;
- offline metrics и пороги;
- latency/memory/thermal budgets;
- on-device test protocol;
- model packaging/provenance requirements;
- go/no-go rule для включения Camera Coach в production.

Не отвечай общим «соберите больше данных». Назови минимальный разумный размер данных на класс/сцену, этапы расширения и способ доказать, что улучшение не является leakage.

### 6. Backend decision

Выбери `NO BACKEND FOR 1.0` либо `MINIMAL OPT-IN DEEP REVIEW`. Дай аргументацию. Для второго варианта предоставь минимальный API/privacy/cost/ops contract. Не предлагай большую платформу или микросервисы без доказанной необходимости.

### 7. Ordered execution tracker

Машиночитаемая Markdown-таблица. Каждая задача должна иметь:

`ID | priority | objective | exact repo areas/files | dependencies | acceptance criteria | narrow verification | required evidence | autonomous/owner/device/legal/account | stop gate`

Трекер должен быть конечным, dependency-ordered и вести от текущего checkout к App Store RC. Не объединяй месяцы работы в одну строку. Не создавай задачи «polish UI» без перечисления конкретных экранов/дефектов и измеримого результата.

### 8. Dependency DAG and milestones

Минимум milestones: reproducible baseline → correctness → ML quality → release/legal/privacy → device qualification → TestFlight → App Store RC. Покажи, что можно вести параллельно и где обязательны последовательные gates.

### 9. NEXT_PACKET_FOR_CODEX

Ровно первые 10 автономных задач, которые Codex может начать без владельца и физического устройства. Они должны начинаться с проверки актуального diff и correctness/reproducibility, а не с дизайна. Для каждой: файлы, изменение, узкая проверка и stop condition. Не включай commit/push/stash/reset/clean.

### 10. External action queue

Отдельные списки для:

- owner product decisions;
- legal/provenance decisions;
- Apple Developer/App Store Connect actions;
- physical-device tests;
- data collection/human labeling.

Не блокируй автономные source-задачи ожиданием внешних действий, если их можно безопасно выполнить раньше.

### 11. Definition of Release Candidate

Набор бинарных go/no-go критериев и kill criteria. Отдельно укажи, какой функционал нужно feature-flag/remove from 1.0, если ML thresholds или device evidence не будут достигнуты.

### 12. Assumptions and confidence

Что известно, что выведено косвенно, чего не хватает в attachments. Для каждого ключевого решения укажи confidence. Не изображай недоступную проверку как выполненную.

## Стиль ответа

Будь жёстким и конкретным. Предпочитай меньший, честно работающий 1.0 большому недоказанному приложению. Не расширяй архитектуру ради будущего. Любой новый backend/model/framework обязан иметь измеримую необходимость, стоимость и exit criterion. Финальный ответ должен быть пригоден как tracker для следующей Codex-сессии без дополнительного пересказа.
